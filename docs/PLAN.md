## 1. 定位与目标

Usnea 是一个“薄引擎”：核心只做 ECS、调度、场景加载和渲染循环，其余功能全部由插件提供。

### 1.1 目标与验收标准

| 目标 | 含义 | 验收标准 |
|---|---|---|
| 便捷 | 不装编辑器，一条命令开始 | `npm create usnea` 到浏览器出现画面不超过 1 分钟 |
| 易写 | 接口少、概念少 | 核心包导出不超过 60 个接口；最小可玩游戏不超过 50 行 |
| 适合 Vibe Coding | AI 能读懂、能改、能自己验证 | 准备 10 个标准任务，AI 只读单文件文档就能写出并自测；通过率公开记录 |
| 能耗最优 | 默认省电，不靠使用者调优 | 静止画面零重绘；公开可复现的能耗基准 |
| 生态 | 插件就是普通 npm 包 | 官方插件与第三方插件使用同一套接口，没有“内部通道” |
| 跨平台 | 一套代码，四个平台 | 同一个项目不改代码，能打包到 Web、Windows、Linux、安卓 |
| 可转写 | 其他引擎的项目能直接导入 | `usnea import` 支持 Cocos Creator、Phaser、Godot、Unity 的 2D 项目 |

### 1.2 非目标（1.0 之前不做）

- 3D 渲染
- 图形化编辑器（场景靠文本和 AI 编辑；将来可由社区用插件做）
- 主机平台（PlayStation、Xbox、Switch）
- 苹果平台（macOS、iOS）的原生打包。Web 版在苹果设备的浏览器里通常也能打开，但不做专门的测试和保证。架构上不排斥以后加入，见第 12 节
- 自研物理、音频解码、网络协议（一律封装现成的开源库）
- 可视化着色器编辑、骨骼动画编辑等内容制作工具

## 2. 设计原则

1. **一切皆文本。** 场景、预制体、配置、资源清单都是 JSON，能被 AI 直接读写，也能在 Git 里看差异。
2. **核心极小。** 能做成插件的就不进核心。核心接口在 1.0 冻结。
3. **数据与逻辑分离。** 组件只存数据，系统只是函数。一个系统一个文件。
4. **默认省电。** 画面没变就不重绘，没事可做就停下主循环。
5. **AI 可自验证。** 每个功能都能在命令行无头运行、截图、导出状态。
6. **报错即教学。** 每条错误信息都说明原因和修法。
7. **一套代码，全平台。** 游戏代码、插件和核心都不直接调用浏览器接口，一切经过平台层。

## 3. 技术选型

具体版本号在动工时锁定，这里只定方向。

| 项目 | 选择 | 理由 |
|---|---|---|
| 语言 | TypeScript（严格模式） | AI 最熟悉；类型检查能当场拦住错误 |
| 渲染基线 | WebGL2 | 覆盖面最广，旧手机和小游戏平台都能跑 |
| 渲染可选后端 | WebGPU（v0.5 评估） | 见下方说明 |
| 目标平台 | Web、Windows、Linux、安卓 | 见 4.9 |
| 桌面与手机打包 | 第一阶段用“壳”：Windows 和安卓用 Tauri（调用系统自带的 WebView）；Linux 用 Chromium 内核的壳 | 最快覆盖全平台，安装包小 |
| 原生运行时 | 第二阶段：Rust + wgpu + 内嵌 JS 引擎（v0.7，实验性） | 去掉浏览器内核的开销，能耗更低 |
| 无头运行 | Node | 测试和 AI 自验证不需要显卡 |
| 打包与开发服务器 | Vite | 热重载快，配置少 |
| 包管理与多包仓库 | pnpm workspace | 一个仓库管理核心、插件、导入器 |
| 测试 | Vitest（单元）+ Playwright（截图） | 都能在命令行和 CI 里跑 |
| 代码规范 | Biome | 一个工具同时做格式化和检查 |
| 发版 | Changesets + 语义化版本 | 多包版本联动 |
| 持续集成 | GitHub Actions | 与 GitHub 仓库直接配合 |
| 物理 | 封装现成的 2D 物理库（候选 Rapier、planck.js） | 不自研；动工时按体积和协议评估 |
| 热点优化 | Rust 编译为 WASM | 只在性能分析确认是瓶颈后才用 |

**关于渲染基线的说明。** 之前的设想是“WebGPU 为主、WebGL 后备”，核实现状后改为“WebGL2 为基线、WebGPU 为可选后端”：

- 截至 2026 年，WebGPU 已在 Chrome、Edge、Safari、Firefox 的主流版本默认启用，但 Firefox 在 Linux 和 Android 上仍未正式提供，部分旧安卓设备也不支持。
- 微信小游戏的 WebGPU 接口（`wx.getGPU`）目前只在安卓版微信可用。
- 2D 游戏很少把 GPU 用满，WebGL2 足够，而且更稳。

渲染器从第一天起就做成可替换的接口，后面加 WebGPU 后端不需要改上层代码。

## 4. 架构设计

### 4.1 分层

| 层 | 包 | 职责 |
|---|---|---|
| 游戏项目 | 用户代码 | 场景 JSON、系统 `.ts`、资源 |
| 兼容层 | `compat/*` | 提供其他引擎风格的写法，供转写后的代码先跑起来 |
| 插件层 | `plugins/*` | 输入、音频、物理、UI、瓦片地图、补间等 |
| 核心 | `usnea` | ECS、调度器、事件、资源管理、场景加载 |
| 渲染后端 | `render-webgl2`、`headless` | 画到屏幕上，或在 Node 里无画面运行 |
| 平台层 | `platform-web`，以后加 `platform-native` | 窗口、输入、音频输出、存储、时钟、网络 |
| 工具链 | `cli`、`importers/*` | 命令行、导入器、文档生成、基准测试 |

依赖方向只能自上而下。核心不依赖任何插件，也不依赖具体的渲染后端和平台。

游戏代码、插件和核心都不直接调用浏览器接口（`window`、`document` 等），只通过平台层。CI 里有规则检查这一条。它是跨平台的前提，也是以后换成原生运行时而不用改游戏代码的前提。

### 4.2 ECS

- **实体**：一个 32 位整数（索引 + 代数），不是对象。
- **组件**：用 schema 声明，数值字段存放在连续的 TypedArray 里（按字段分列存储），避免垃圾回收。字符串和引用放在旁路表里。
- **系统**：一个函数，声明自己读哪些组件、写哪些组件。调度器据此排序，并跳过没有匹配实体的系统。
- **阶段**：`input → fixed（固定步长）→ update → render`。
- **事件**：类型化的队列，帧末清空。
- **资源**：全局单例（时间、输入状态、资源表）。

接口草案（以最终实现为准）：

```ts
import { defineComponent, defineSystem, f32 } from "usnea";

export const Position = defineComponent("Position", { x: f32, y: f32 });
export const Velocity = defineComponent("Velocity", { x: f32, y: f32 });

export const movement = defineSystem({
  name: "movement",
  query: [Position, Velocity],
  writes: [Position],
  run(world, dt, entities) {
    for (const e of entities) {
      Position.x[e] += Velocity.x[e] * dt;
      Position.y[e] += Velocity.y[e] * dt;
    }
  },
});
```

### 4.3 场景格式

```json
{
  "usnea": "0.1",
  "name": "main",
  "plugins": ["@usnea/physics2d"],
  "entities": [
    {
      "id": "player",
      "components": {
        "Position": { "x": 100, "y": 200 },
        "Velocity": { "x": 0, "y": 0 },
        "Sprite": { "image": "assets/player.png" }
      }
    },
    {
      "id": "enemy-1",
      "prefab": "prefabs/enemy.json",
      "components": { "Position": { "x": 400, "y": 200 } }
    }
  ]
}
```

- 资源一律用**相对路径**引用，不用 UUID。AI 和人都能看懂。
- 预制体是另一个 JSON 文件，场景里可以覆盖其中的字段。
- 从组件定义自动生成 JSON Schema，用来校验场景文件；写错字段名立刻报错。
- 键的顺序固定，Git 差异干净。

### 4.4 主循环与按需渲染

这是能耗设计的核心。

- **脏标记**：系统声明了 `writes`，引擎由此知道哪些系统会改变画面。只有“可见组件”被写入时才标脏，不脏不画。
- **唤醒源**：输入事件、进行中的动画或补间、未休眠的物理体、定时器、网络消息。
- **空闲即停**：没有任何唤醒源时，不再请求下一帧，主循环完全停止；有事件到来再启动。
- **固定步长**：逻辑默认 60Hz，可配置为 30Hz；渲染在两次逻辑之间插值。
- **后台暂停**：页面不可见时停止逻辑和渲染。
- **帧率上限**：默认跟随屏幕，可设为 30。

### 4.5 2D 渲染器

v0.1 的范围：精灵批处理、纹理图集、相机、图层与排序、文本（位图字体和缓存的画布文字）、九宫格。自定义着色器和后处理放到 1.0 之后。

### 4.6 资源管理

- 资源清单是文本文件，构建时生成。
- 懒加载加引用计数；场景切换时自动释放不再使用的资源。
- 导入器负责把其他引擎的 UUID 引用换成路径引用。

### 4.7 命令行

| 命令 | 作用 |
|---|---|
| `npm create usnea` | 新建项目 |
| `usnea dev` | 开发服务器，热重载 |
| `usnea run --headless --frames 600` | 无画面运行指定帧数 |
| `usnea shot <场景> -o out.png` | 运行后截图 |
| `usnea inspect <场景>` | 把世界状态导出为 JSON |
| `usnea test` | 运行单元测试和回放测试 |
| `usnea build --target <平台>` | 打包到指定平台：`web`、`windows`、`linux`、`android` |
| `usnea import <项目路径>` | 从其他引擎转写 |
| `usnea plugin add <名称>` | 安装并登记插件 |
| `usnea doctor` | 检查环境和项目配置 |

### 4.8 无头模式与确定性

- 随机数用固定种子，逻辑用固定步长。同样的输入必然得到同样的结果。
- 输入可以录制成文本文件再回放，用于回归测试。
- 无头模式不需要显卡，CI 和 AI 都能直接运行。

### 4.9 平台支持

一套游戏代码，四个平台：Web、Windows、Linux、安卓。分两个阶段实现。

**第一阶段：壳方案（v0.3）。** 游戏仍然是 Web 构建产物，外面套一层原生的“壳”，壳里用 WebView 显示游戏。

| 平台 | 打包方式 | 内核 | 备注 |
|---|---|---|---|
| Web | 静态文件 | 浏览器 | 基线 |
| Windows | Tauri | WebView2（Chromium） | WebGL 表现通常最好 |
| 安卓 | Tauri | 系统 WebView（Chromium） | 打包需要 Android SDK 和 NDK |
| Linux | Chromium 内核的壳（如 Electron）；Tauri 可选 | Chromium | 见下方说明 |

- 好处：最快覆盖全部平台；游戏代码完全相同；Tauri 的安装包很小。
- 代价：各平台的 WebView 内核不同，行为和性能有差异；仍然带着浏览器内核的开销。
- Linux 的特殊处理：Tauri 在 Linux 上用 WebKitGTK。Tauri 官方文档记载它在部分显卡（尤其是 NVIDIA）上有图形问题，并建议用到 WebGL 的应用在 Linux 上准备后备方案。所以 Linux 默认用 Chromium 内核的壳，安装包较大但稳定。

**第二阶段：原生运行时（v0.7，实验性）。** 不再依赖 WebView。

- 渲染用 Rust + wgpu，一套代码对接 Vulkan（安卓、Linux）和 DirectX 12（Windows）。
- 游戏逻辑仍然是 TypeScript，运行在内嵌的 JS 引擎里（候选 QuickJS、JavaScriptCore、V8、Hermes，动工时评估）。
- 组件数据本来就存放在连续内存里，Rust 一侧可以直接读取，不需要逐个对象转换。
- 游戏代码不用改，因为它只接触核心接口和平台层。

原生运行时的工作量大。是否推进、先做哪些平台，由 v0.5 的能耗实测数据决定。

**平台能力统一接口。** 存档、全屏、窗口大小、触摸和手柄、振动、应用进入后台和回到前台的事件，都通过平台层提供，各平台各自实现。

**应用商店。** 上架 Google Play 或国内的安卓应用商店需要各自的开发者账号、签名和审核，由游戏作者完成。`usnea doctor` 会检查打包环境是否齐全。

## 5. Vibe Coding 支持

### 5.1 给 AI 的入口

- **`AGENTS.md`**：放在引擎仓库和每个新建项目的根目录，说明目录结构、常用命令、编码约定、禁止事项。
- **`llms.txt`**：单文件的完整接口文档，由类型定义自动生成，保证和代码一致。
- **配方库（recipes）**：常见需求的最小示例（角色移动、碰撞、存档、UI 按钮），每个不超过 80 行。

### 5.2 编码约定

- 一个系统一个文件，文件不超过 200 行。
- 组件定义集中放在 `components/`，系统放在 `systems/`，场景放在 `scenes/`。
- 禁止隐式的全局状态；系统只通过 `world` 访问数据。
- 类型就是文档：公开接口必须有类型和一句话注释。

### 5.3 让 AI 自己验证

AI 改完代码后的标准流程，全部是命令行，不需要人看屏幕：

1. `usnea test`：单元测试和回放测试。
2. `usnea run --headless`：确认不报错。
3. `usnea shot`：截图，AI 自己看图判断画面是否正确。
4. `usnea inspect`：导出状态，核对数值。

### 5.4 错误信息规范

每条错误都有编号、原因和修法。例如：

```
USN-E012 场景 scenes/main.json 中的实体 "player" 使用了未注册的组件 "Positon"。
你是不是想写 "Position"？
如果这是插件提供的组件，请在场景的 "plugins" 中加入对应插件。
```

### 5.5 本项目自身的开发方式

引擎本身也用 Vibe Coding 开发，约定如下：

- 每次改动范围小，一次只做一件事，附带测试。
- 先写测试或示例，再写实现。
- 每个里程碑结束时人工通读一遍核心代码。
- AI 生成的代码同样要过 CI、代码规范检查和依赖协议检查。

## 6. 插件生态

### 6.1 插件是什么

一个插件就是一个 npm 包，只做三件事：注册组件、注册系统、提供资源。

```ts
import { definePlugin } from "usnea";
import { Health } from "./components";
import { damage } from "./systems/damage";

export default definePlugin({
  name: "usnea-plugin-health",
  components: [Health],
  systems: [damage],
  setup(app) {
    // 可选的初始化
  },
});
```

`package.json` 里的声明：

```json
{
  "name": "usnea-plugin-health",
  "keywords": ["usnea-plugin"],
  "peerDependencies": { "usnea": "^0.2.0" },
  "usnea": {
    "components": ["Health"],
    "systems": ["damage"]
  }
}
```

### 6.2 命名与发现

- 官方插件：`@usnea/名称`（需要先注册 npm 组织，见待确认事项）。
- 社区插件：`usnea-plugin-名称`，并带上关键词 `usnea-plugin`。
- 不自建商店。用 npm 关键词搜索，加上文档里维护的一份精选列表。

### 6.3 官方插件清单

| 插件 | 内容 | 里程碑 |
|---|---|---|
| `@usnea/input` | 键盘、鼠标、触摸、手柄 | v0.2 |
| `@usnea/audio` | 音效与音乐 | v0.2 |
| `@usnea/physics2d` | 2D 物理（封装现成库） | v0.2 |
| `@usnea/ui` | 按钮、文本、布局 | v0.2 |
| `@usnea/tween` | 补间动画 | v0.2 |
| `@usnea/device` | 存档、全屏、振动、前后台事件 | v0.3 |
| `@usnea/tilemap` | 瓦片地图 | v0.4 |
| `@usnea/particles` | 粒子 | v0.5 |
| `@usnea/platform-wechat` 等 | 小游戏平台适配 | v0.5 |

### 6.4 兼容性规则

- 语义化版本。1.0 之前允许破坏性修改，但每次都写迁移说明。
- 插件用 `peerDependencies` 声明支持的引擎版本范围；`usnea doctor` 检查冲突。
- 插件在 manifest 里声明自己注册的组件和系统名，重名时启动报错，不静默覆盖。

### 6.5 玩家模组

- 1.0 之前只支持**数据模组**：替换或新增 JSON 场景、预制体和资源。
- 可执行代码的模组（WASM 沙箱）放到 1.0 之后，因为涉及安全审查。

## 7. 能耗设计

### 7.1 策略

| 策略 | 做法 |
|---|---|
| 按需渲染 | 画面没变不重绘（见 4.4） |
| 空闲即停 | 没有唤醒源时主循环完全停止 |
| 事件驱动 | 输入、定时器、网络都走事件，不轮询 |
| 实体休眠 | 静止的物理体和屏幕外的动画不参与计算 |
| 系统跳过 | 没有匹配实体或没有数据变化的系统不执行 |
| 少垃圾回收 | 数值存 TypedArray；热路径不创建临时对象 |
| 批处理 | 同图集的精灵合并成一次绘制 |
| 后台暂停 | 页面不可见时全部停下 |
| 低频逻辑 | 逻辑可降到 30Hz，渲染插值保持流畅 |

### 7.2 能耗指标（目标值，需用基准测试校准）

- 静止场景（如菜单）：每秒重绘 0 次，主线程 CPU 时间接近 0。
- 1000 个移动精灵：在中端手机上稳定 60 帧，每帧 CPU 时间不超过 4 毫秒。
- 同一场景的耗电不高于同类 Web 引擎；数据公开。

### 7.3 基准测试方法

- 固定场景集：静止菜单、1000 个移动精灵、物理堆叠、瓦片地图滚动。
- 指标：每秒重绘次数、每帧 CPU 时间、绘制调用次数、内存、真机电量消耗。
- 对照：用其他引擎实现同样的场景，脚本和原始数据都放在 `benchmarks/` 里，任何人都能复现。
- 回归：CI 里跑 CPU 时间基准，比上一版退化超过 10% 则失败。

### 7.4 调试开关

- `?usnea-debug=redraw`：在屏幕角落显示重绘次数，一眼看出有没有多余重绘。
- `?usnea-debug=always-render`：强制每帧渲染，用来排查“该刷新却没刷新”的问题。

### 7.5 各平台的能耗

- 引擎自身的省电策略（按需渲染、空闲即停）在所有平台同样生效。
- 壳方案的额外能耗取决于各平台的 WebView 内核。v0.5 在四个平台分别实测并公开数据。
- 哪个平台的壳方案达不到指标，哪个平台就优先做原生运行时（见 4.9）。

## 8. 从其他引擎转写

### 8.1 总体思路

目标不是百分之百全自动，而是**把机械工作全部自动化，把剩下的工作列成清晰的清单**。

转写分三层，可靠程度不同：

| 层 | 内容 | 方法 | 预期 |
|---|---|---|---|
| 场景与资源 | 场景、预制体、图片、音频、图集 | 确定性转换，不用 AI | 支持范围内接近全自动 |
| 概念映射 | 原引擎的概念对应到 Usnea 的什么 | 每个引擎一张映射表 | 人工维护，随版本更新 |
| 脚本 | 游戏逻辑代码 | AI 按映射表转写 | 需要人工复核 |

### 8.2 流水线

`usnea import <项目路径>` 依次执行：

1. **探测**：识别引擎种类和版本。
2. **解析**：读取场景、预制体、资源和元数据文件。
3. **转换**：生成 Usnea 的场景 JSON，把 UUID 引用换成路径，复制资源。
4. **脚本转写**：按映射表生成转写任务，交给 AI 逐个文件转写；默认先接到兼容层上。
5. **验证**：无头运行、截图，与原游戏的截图比对。
6. **报告**：输出 `IMPORT_REPORT.md`。

### 8.3 概念映射表（摘要）

| 概念 | Cocos Creator | Godot | Unity | Phaser | Usnea |
|---|---|---|---|---|---|
| 场景对象 | Node | Node | GameObject | GameObject | 实体 |
| 数据与行为 | Component 脚本 | 节点上的脚本 | MonoBehaviour | 场景类的方法 | 组件（数据）+ 系统（行为） |
| 层级关系 | 节点树 | 节点树 | Transform 父子 | Container | `Parent` 组件 |
| 预制 | Prefab | PackedScene | Prefab | 工厂函数 | 预制体 JSON |
| 消息 | EventTarget | Signal | UnityEvent、C# 事件 | EventEmitter | 类型化事件 |
| 每帧更新 | `update(dt)` | `_process(delta)` | `Update()` | `update(time, delta)` | `update` 阶段的系统 |
| 固定更新 | 物理步进 | `_physics_process(delta)` | `FixedUpdate()` | 物理步进 | `fixed` 阶段的系统 |
| 场景文件 | `.scene`（JSON） | `.tscn`（文本） | `.unity`（YAML） | 无，代码构建 | `.scene.json` |
| 脚本语言 | TypeScript | GDScript、C# | C# | JavaScript、TypeScript | TypeScript |

完整的映射表放在各导入器目录下的 `MAPPING.md`，同时是 AI 转写脚本时的参考资料。

### 8.4 兼容层

每个引擎一个可选插件（`@usnea/compat-cocos` 等），用 Usnea 的接口实现原引擎最常用的那部分写法，例如 `start/update` 生命周期、`this.node.position`、`getComponent`。

- 作用：转写后的代码先跑起来，再逐步改成原生的组件加系统写法。
- 兼容层是独立实现，只参考公开文档里的接口形状，不复制原引擎的代码。
- 兼容层有额外开销，`IMPORT_REPORT.md` 会标出哪些文件还在用它。

### 8.5 转写报告

`IMPORT_REPORT.md` 包含：

- 已转换的场景、预制体、资源数量。
- 不支持的功能清单，标明所在文件和行号（例如自定义着色器、3D 节点、第三方插件）。
- 每个脚本的状态：已转写、需复核、未转写。
- 截图比对结果。
- 建议的下一步。

### 8.6 各引擎的要点与顺序

| 顺序 | 引擎 | 有利条件 | 难点 | 里程碑 |
|---|---|---|---|---|
| 1 | Cocos Creator | 场景是 JSON，脚本本来就是 TypeScript | UUID 引用、编辑器专有的组件 | v0.4 |
| 2 | Phaser | 同为 Web 技术，JavaScript 或 TypeScript | 没有场景文件，全靠转写代码 | v0.4 |
| 3 | Godot | 场景和资源是文本格式 | GDScript 转 TypeScript；信号和节点路径 | v0.6 |
| 4 | Unity | 用户最多 | C# 转 TypeScript；协程；动画状态机；只支持文本序列化的项目 | v0.6 |

每个导入器只支持 2D 功能的一个子集，并在文档里公开“支持矩阵”：哪些组件能转、哪些部分能转、哪些不能转。

### 8.7 边界

- 只读取和转换**用户自己的项目文件**。
- 不包含、不复制原引擎的源码、运行时和内置素材。
- 第三方素材和插件（例如资源商店里买的）的授权由用户自己确认，报告里会提醒。
- 文档里提到其他引擎的名称只是说明用途，不代表有官方合作关系。
- 用户在转写商业项目前，应自行查看原引擎的服务条款。

### 8.8 验收标准

- 每个导入器选 3 个该引擎的公开示例项目（协议允许的）作为测试集。
- 场景和资源：支持矩阵内的内容全部自动转换。
- 转写后项目能启动并通过截图比对的比例，随版本公开记录。

### 9.3 治理

- 早期由维护者一人决定方向。
- 重大改动先在 GitHub Discussions 发提案，再动手。
- 1.0 之后如果有稳定的贡献者，再考虑设核心小组。

`README.md`（英文）、`README.zh-CN.md`（中文）、`LICENSE`、`NOTICE`、`CONTRIBUTING.md`、`CODE_OF_CONDUCT.md`、`SECURITY.md`、`CHANGELOG.md`、`AGENTS.md`。

## 11. 里程碑

规模用“小、中、大”表示相对工作量，不承诺日期。每个里程碑都能独立发布。1.0 之后的方向见第 12 节。

### v0.0 起步（小）

- 交付：空仓库结构、协议文件、中英文 README、`AGENTS.md`、CI、npm 占位包。
- 验收：CI 通过；`npm view usnea` 能查到占位版本。

### v0.1 核心（大）

- 交付：ECS、调度器、事件、JSON 场景加载与校验、平台层接口和 Web 实现、WebGL2 精灵渲染、按需渲染主循环、无头模式、`dev`、`run`、`shot`、`inspect`、`test` 命令、一个示例游戏。
- 验收：示例游戏在桌面和手机浏览器运行；静止时重绘为 0；无头回放测试结果稳定一致；核心和示例代码没有直接调用浏览器接口（CI 检查）。

### v0.2 生态（中）

- 交付：插件接口、`plugin add` 和 `doctor` 命令、官方插件（输入、音频、物理、UI、补间）、`llms.txt` 自动生成、配方库、错误编号体系。

### v0.3 多平台打包（中）

- 交付：`usnea build --target` 支持 Web、Windows、Linux、安卓；各平台的壳；`@usnea/device` 插件；`doctor` 检查打包环境；CI 为各平台自动打包。
- 验收：同一个示例游戏不改代码，在四个平台都能安装并运行；每个平台有一份已知问题清单。

### v0.4 转写一期（大）

- 交付：导入器框架、转写报告、Cocos Creator 导入器、Phaser 导入器、对应的兼容层、瓦片地图插件。
- 验收：两个引擎各 3 个示例项目完成转写，结果记录在案。

### v0.5 能耗与小游戏平台（中）

- 交付：基准测试套件、四个平台的实测数据、CI 性能回归、微信和抖音小游戏适配、粒子插件、WebGPU 后端评估结论、是否推进原生运行时的结论。
- 验收：能耗指标达标或有明确的差距说明；示例游戏在小游戏平台运行。

### v0.6 转写二期（大）

- 交付：Godot 导入器、Unity 导入器、对应的兼容层和支持矩阵。
- 验收：同 v0.4。

### v0.7 原生运行时（大，实验性）

- 交付：Rust + wgpu 渲染、内嵌 JS 引擎、`platform-native` 平台层。按 v0.5 的数据决定平台顺序，预计先做 Linux 和 Windows，再做安卓。
- 验收：示例游戏不改代码就能在原生运行时上运行；截图与 Web 版一致；有和壳方案的能耗对比数据。
- 说明：如果 v0.5 的数据显示壳方案已经达标，本里程碑可以推迟到 1.0 之后。v1.0 不依赖它。

### v1.0 稳定版（中）

- 交付：核心接口冻结、完整文档、迁移指南、数据模组支持。
- 验收：连续两个小版本没有破坏性修改；文档覆盖全部公开接口。

## 12. 远期展望（1.0 之后）

这一节是方向，不是承诺。每一项都写了“触发条件”，条件满足了才动工，避免凭空扩张。

### 12.1 不变的原则

无论做到多大，下面几条不变：

- **核心保持极小。** 新能力优先做成插件。
- **文本优先。** 即使将来有图形编辑器，场景文件仍然是人和 AI 都能读的文本。
- **默认省电。** 任何新功能都不能让静止的画面产生重绘。
- **协议不变。** 代码保持 Apache-2.0，不收版税，不改成限制性协议。不设 CLA 也意味着维护者无法单方面改协议。
- **不强制联网，不强制账号。** 遥测默认关闭。

### 12.2 1.x：稳固与补全

1.x 期间核心接口不做破坏性修改。

| 方向 | 内容 | 触发条件 |
|---|---|---|
| 原生运行时转正 | Windows、Linux、安卓的原生运行时从实验性变为正式支持 | v0.7 的能耗数据明显优于壳方案 |
| WebGPU 后端 | 成为正式的可选渲染后端 | 目标平台的覆盖率足够高，并且实测有收益 |
| 代码模组 | 玩家模组可以带逻辑，运行在 WASM 沙箱里，有权限声明 | 有游戏提出实际需求 |
| 联机 | 帧同步和回滚式联机插件。引擎的确定性模拟天然适合这两种方式 | 确定性经过 1.0 的检验 |
| 回放与录像 | 用输入回放实现录像分享、死亡回放、错误复现 | 同上 |
| 更多导入器 | GameMaker、RPG Maker、LÖVE，以及国内常用的 LayaAir、白鹭 Egret | 社区投票决定顺序；每个导入器要有人维护 |
| 更多小游戏平台 | 支付宝、快手、各手机厂商的快游戏 | 微信和抖音的适配稳定之后 |
| 鸿蒙 | 作为第五个平台。新版鸿蒙不再兼容安卓应用，需要单独适配 | 有维护者拥有设备并愿意长期维护 |
| 开发工具 | 浏览器里的状态查看器、性能面板、能耗面板 | 1.0 发布后即可开始 |
| 长期支持版 | 指定版本只修问题、不加功能，适合商业项目 | 出现商业项目用户 |

### 12.3 2.0：能力扩展

2.0 允许破坏性修改，但必须同时提供迁移工具。导入器框架可以直接复用：把“Usnea 1 的项目”当作一种来源引擎，转写到 2.0。

| 方向 | 内容 | 触发条件 |
|---|---|---|
| 3D | 先做 2.5D（把 3D 模型放进 2D 游戏），再做轻量 3D；模型格式用 glTF | 2D 部分稳定；原生运行时或 WebGPU 后端成熟 |
| 多线程 | 系统已经声明了读写哪些组件，调度器可以据此自动并行 | 出现单线程解决不了的性能需求 |
| Rust 核心 | 把 ECS 的存储和调度下沉到 Rust；Web 上编译成 WASM，原生平台直接使用 | 性能分析显示 JS 核心成为瓶颈 |
| 图形编辑器 | 可选的场景编辑器，本身用 Usnea 加插件做成，读写同一套文本文件 | 社区有人主导；不进核心 |
| 苹果平台 | macOS 和 iOS | 有维护者拥有设备和开发者账号 |
| 主机平台 | 主机的开发工具受保密协议限制，开源引擎一般由第三方公司提供移植 | 有合作方 |

### 12.4 AI 原生方向

这是 Usnea 和其他引擎拉开差距的地方。

- **引擎即工具。** 内置一个给 AI 用的服务接口（例如 MCP 服务器）。AI 可以直接查询世界状态、截图、注入输入、运行测试，不需要人转述。
- **AI 试玩。** 让 AI 自动玩游戏，找卡死、穿模、数值失衡，输出可以回放的问题报告。
- **自然语言到场景。** 描述一个关卡，生成场景 JSON 和预制体。因为有 schema 校验，生成的结果能自动检查。
- **转写持续进化。** 映射表交给社区维护；公开一套转写基准，记录每个导入器在标准项目上的成功率。
- **AI 友好度基准。** 把第 1 节的“10 个标准任务”扩展成公开基准，每次发版都测。接口设计得好不好，用数据说话。

### 12.5 能耗方向

- **能耗报告。** `usnea build` 输出每个场景的能耗估算，标出最耗电的系统。
- **自适应降频。** 设备发热或电量低时，自动降低逻辑和渲染频率（前提是平台允许读取这些状态）。
- **公开的跨引擎能耗对比。** 同样的场景、同样的设备、可复现的方法。
- **低端设备档位。** 为旧手机提供自动降级的画质档。

### 12.6 生态与社区

- 插件数量上来之后，再做带搜索、评分和兼容性标记的插件目录网站。仍然基于 npm，不另建仓库。
- 中英文文档同等对待；在 Gitee 设镜像，方便国内访问。
- 教学方向：引擎小、概念少、全是文本，适合用来教编程和游戏开发；提供课程式的教程。
- 示例游戏库：每种常见类型（平台跳跃、塔防、卡牌、Roguelike）一个完整的开源示例。
- 每年办一次用 Usnea 做游戏的创作活动（Game Jam）。

### 12.7 治理与可持续性

- **治理：** 个人维护 → 核心小组（有 3 位以上稳定贡献者时）→ 条件成熟时交给中立的基金会托管。
- **经费：** 接受赞助（GitHub Sponsors、Open Collective、爱发电等），账目公开。
- **增值服务：** 可以有不影响开源的服务，例如云端打包和托管。引擎本身永远完整开源。
- **商标：** 把名字和标志的使用规则写清楚，防止被冒用。

### 12.8 三年后希望看到的样子

- 一个人对 AI 说清楚想法，当天就能做出能玩的 2D 游戏，并打包到四个平台。
- 其他引擎的 2D 项目，大部分能在一天内转写过来并跑起来。
- 同样的游戏，用 Usnea 比用同类 Web 引擎更省电，并且有公开数据证明。
- 插件生态能覆盖常见需求，而核心仍然小到一个人能读完。

## 13. 质量保证

| 手段 | 内容 |
|---|---|
| 单元测试 | 核心逻辑全覆盖：ECS、调度、场景加载 |
| 回放测试 | 录制输入，无头回放，比对最终状态 |
| 截图测试 | 示例场景截图与基准图比对 |
| 性能回归 | CI 里跑 CPU 时间基准 |
| 导入器测试 | 固定的示例项目集，每次改动后重新转写并比对 |
| 多平台构建 | CI 为四个平台各打一次包；Web、Windows、Linux 做启动测试，安卓至少保证打包成功 |
| 类型检查 | 严格模式，CI 里零错误 |
| 依赖检查 | 协议白名单、已知漏洞扫描 |

所有检查都在 GitHub Actions 里自动运行，合并前必须通过。

## 14. 风险与对策

| 风险 | 对策 |
|---|---|
| 范围太大，一个人加 AI 做不完 | 严守非目标；每个里程碑独立可用；先做 2D |
| 转写效果达不到预期 | 公开支持矩阵，不夸大；用兼容层和报告清单兜底 |
| 按需渲染导致画面该刷新却没刷新 | 脏标记由 `writes` 声明自动推导；提供强制渲染的调试开关 |
| JavaScript 的性能上限和垃圾回收卡顿 | TypedArray 存储；性能回归测试；确认瓶颈后用 WASM |
| 小游戏平台与浏览器环境不一致 | 平台适配做成插件；核心只依赖 WebGL2 的通用部分 |
| 各平台 WebView 内核不同，行为和性能有差异 | 每个平台都在 CI 里构建和测试；维护各平台的已知问题清单 |
| Linux 上 WebKitGTK 的图形问题 | Linux 默认用 Chromium 内核的壳；原生运行时优先考虑 Linux |
| 原生运行时工作量大，可能拖垮进度 | 放在 v0.7 且为实验性；由实测数据决定做不做；v1.0 不依赖它 |
| 远期方向太多，分散精力 | 第 12 节每一项都有触发条件，条件不满足不动工 |
| npm 包名或组织名被别人先注册 | v0.0 立即占位 |
| 转写他人引擎项目的法律问题 | 见 8.7 的边界；只转换用户自己的文件 |
| AI 生成的代码质量不稳 | 小步提交、测试先行、里程碑末人工通读 |
| 只有一个维护者 | 文档和 `AGENTS.md` 写全，让新贡献者和 AI 都能快速接手 |

## 15. 待确认事项

1. 名称是否定为 Usnea。
2. 是否采用 Apache-2.0。
3. GitHub 用户名和仓库名（建议 `usnea`）。
4. 是否注册 npm 组织 `usnea`，用于 `@usnea/*` 官方插件；如果注册不到，官方插件改用 `usnea-名称`。
5. README 是否中英双语（建议英文为主页，中文为 `README.zh-CN.md`）。
6. 四个平台里最看重哪一个。全部都会支持，但这决定测试重点，以及原生运行时先做哪个平台。
7. 转写的优先顺序是否按 Cocos Creator → Phaser → Godot → Unity。
8. 是否需要微信、抖音等小游戏平台（目前排在 v0.5）。
9. 第 12 节的远期方向里，你最想先看到哪几项。
